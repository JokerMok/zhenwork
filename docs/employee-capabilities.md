## 2026-10-27 登录直达与整组共享

发布 `20261027-entry-sharing-v10`，应用源码 `b2edb832ed634ed3844e4970693e3c3a84093706`。新增 0024 加法迁移，既有 23 条摘要不变；复用原 Rust、amd64 Core/Gateway 和监控。最终 v10 仅更新 Host，按 manifest 精确复用 v9 的其余不可变产物；中间版本未作为通过依据。

员工登录默认进入 `/#/workspace`，原会话深链接经登录和身份失效处理保留。工作台任务/文件/组织能力等 Host 目录不启动 Core；原生新会话及会话内容仍需要独立 Core，准备与失败重试显示在当前输入区，导航外壳保持可用。桌面启动保护不改，不把环境伪装成 ready。浏览器不再保存可逆密码，并清理旧 `rememberedPassword`，账号记忆保留。

管理员在「AI 资源管理 → 企业资源」点击「共享授权」：统一搜索员工、部门或角色，默认“允许使用”，高级编辑和已有共享折叠。普通共享一次提交；重复提交复用活动授权与持久幂等回执。后台重新解析依赖、检查管理员转授权及接收对象基础资格，整组事务保存，成功后才通知运行时更新；失败不留下半组授权。

接收对象已有有效权限直接复用；可转授模型/通用工具按最小 VIEW+USE 追加来源关联许可。敏感知识/Skill/MCP 需在同一弹窗明确确认范围。当前连接权限不能限定为“仅本专家调用”：确认框明确说明将获得该连接现有业务单位、环境和已开放方法的独立只读使用权；不复制凭据、不开放任意数据源，也不自动扩大业务单位或方法。

关联授权记录来源专家、依赖版本及授权版本。专家只更新名称/指令但依赖不变时保留；依赖集合、依赖授权版本或连接授权版本变化后必须重新检查。撤回来源只停用其关联许可，其他独立授权保留。旧缓存客户端默认仍只读取独立共享，新弹窗显式请求来源关联行，防止误把继承许可作为独立记录调整。

原生聊天的 `office_context` 提供当前获授权计算器元数据，`calculate_enterprise_tool` 通过现有办公 MCP 调用 RC2 的共享 BigDecimal 实现；普通登录和后台任务分别校验当前员工或任务授权，计算器 USE 和工具类型在每次调用时复核。不将计算工具当作 Skill 搜索或执行猜测命令；审批型写入工具不能经此只读接口执行。文件成果继续使用已有办公工具和版本/下载链路。

真实查询定位到：执行前资源刷新关闭并重建 MCP 代理，而已初始化的原生 Agent 继续连接旧端口。现在兼容的资源版本及连接在同一员工 Core 内复用代理地址；实际调用仍重新检查资源、连接及工具权限，撤销资源清理代理，Core 回收统一关闭。初始化与工具发现使用当前认证员工；业务执行继续绑定当前会话和服务端后台授权。协议保留空 202/204 响应，前端脱敏的临时 MCP 地址不再覆盖服务端受控配置。

关闭请求可能发生在异步身份校验尚未返回时；Host 不再将已关闭响应重新登记为在途操作，空闲检查清理已结束响应，真实在途请求和任务保护保留。单 Core、启动并发、空闲 120 秒、队列和 no-store 策略不变。

本轮定向验收：普通员工从真实网页选择共享专家，调用精确计算工具并生成/下载 CSV；管理员同弹窗确认查询专家两连接后，员工实际调用优废 `entSummary` 与国家平台 `entInfo`，原聊天分别显示真实结果。专用来源授权撤回后实际工具接口拒绝，恢复后可用；第二账号的资源、专家会话及实际工具接口均拒绝。部门/角色共享和独立许可保留已通过。最终 v10 文字流中关闭整个测试 Chrome 后，服务端已存文字由 353 增至 3412 字；重新登录原聊天完整显示、只有一次发送且无取消。再读原聊天无重发，旧 CSV 下载 SHA256 保持。

没有逐方法复测所有外部查询、重做全后台或测试外部写入；两源本次仅验上述固定只读方法。第一次原生会话创建仍需取得员工独立 Core，不保证容量忙时所有新会话均能立即受理。

私有定向网页、产物及故障记录在 `.codex/login-sharing/`，生产记录在 `shared/config/acceptance/20261027-entry-sharing.md`；是否通过以该记录和 VERIFIED.json 为准，构建成功不等于网页验收。应用回滚审核文件见部署维护文档；回滚保留数据库、关联许可、消息、文件和历史，旧应用不理解新关联许可，相关专家可能暂不可用。

## 组织默认能力

后台「模型管理 → 模型与授权」（`/admin/workspace-models/registry`），对已启用且具备流式/工具能力的模型点击「设为企业默认」。默认模型通过 `ai_office_defaults` 和有效 `workspace_employee` 基础角色引用生效，不为每个员工复制授权、上游地址或密钥。其他模型仍须符合现有授权。

普通用户新增、导入、注册和显式角色更新共用基础角色分配。管理员新增时可不手选角色；编辑时省略角色字段保留既有角色。0022 幂等补齐已有普通员工的基础角色和缺失 principal 关联，不更改个人文件、会话和设置。

企业助手、Skill、MCP、工具与知识使用原资源发布及 VIEW/USE 授权。可授角色、部门或指定员工；企业敏感连接不随基础角色自动开放。使用业务专家需同时拥有其依赖的模型、工具和数据权限；单独授权能力无需绑定助手才能使用。

员工工作台能力/知识页默认显示实际可用资源，标注组织或个人来源。组织通用办公助手和原生文件工具无需个人配置；高级配置仍保留。页面、运行时和离线任务复用 `available` 解析；发布、启用及依赖状态均参与检查，执行时再次校验。新增授权可在空闲时同步到已运行 Core；撤销可清退旧环境/身份，重新登录后按新权限装载。

## 本轮确认的根因

- 企业默认模型原来仅对少数旧试点用户有显式 USER 策略；普通员工即使已有基础角色仍为空。个人资源视图又遗漏组织资源。创建用户的前端及 DTO 还要求手选非空角色，与服务层自动补角色不一致。
- 登录来源在 Host 到 RC2 的内部认证转发中丢失。原始 test1001 日志的一次 401 紧随正常退出，不能把所有 UNAUTHENTICATED 都归为模型配置。另在实际部门变更回归中确认：员工 API 返回 302 登录页，自动跟随后变成 HTML200，导致前端无法识别 401；现在 `/enterprise/*` 和 `/api/*` 的受保护 API 均返回真实 401，文档入口仍跳转登录。
- Admin 监控原未部署、未建立受保护代理。接线回归还发现公共 base URL 使用 HTTP、异步响应丢失身份，以及 RC2 的 HTTP200 错误信封被通用 forward_auth 当作成功。现在使用 HTTPS public-url、在异步分派重新校验私有代理身份，并且 Caddy 只接受权限控制器明确的 204，其他响应拒绝。该配置采用 [Caddy 官方展开方式](https://caddyserver.com/docs/caddyfile/directives/forward_auth)，未关闭认证。
- 系统工具原为无子页面的目录路由。0023 将其映射到真实权限控制落地页，连接既有缓存监控、在线用户、服务监控；未启用代码生成等未部署模块。

## 登录来源与监控边界

当前直连 Caddy，无上游 CDN。公网来源采用 Caddy 实际 socket，覆盖外来转发头；Host 仅接受 loopback 和恒定时间验证的私有 edge token，校验单一 IPv4/IPv6，传递原 User-Agent。在线会话和登录日志仍由同一 RuoYi 登录链记录。历史审计不重写；本轮公网浏览器实测 IPv4，IPv6 校验使用定向用例，未宣称公网 IPv6 实测。

监控服务 `zhenwork-monitor.service` 仅监听 `127.0.0.1:18909`，堆 256MiB、MemoryMax 384MiB。管理员经 `/admin/monitor/Admin` 的同源 `/monitor/` 访问，RC2 校验 `monitor:admin:list`；SBA 注册使用独立服务凭据，浏览器代理使用另一私有随机令牌。公网仅 GET/HEAD；Actuator 不公开。无登录及普通员工有效登录均不能访问；原有 CSRF、安全响应头保留。

配置在 `shared/config/{application-rc2.yml,web.env,monitor.env,monitor-proxy.env,edge.env}`，密钥仅为服务端私有文件。`prepare-monitor.py` 保留既有秘密并幂等生成必要配置。完整运行、备份和回滚命令见 `deploy/tencent/README.md`。
