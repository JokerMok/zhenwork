# 员工聊天、账号记忆与同页准备

本轮基线为 `20261027-entry-sharing-v10`。复用原会话、TaskRunner、文件版本、组织授权及 Core1 容量；没有新建后台执行或定时系统。

## 使用方式

- `/enterprise/login` 成功登录后记住最近账号，密码始终为空；“清除账号”可主动移除。退出保留账号，浏览器不保存密码或模型凭据。React 登录入口采用相同行为，桌面原有可选账号记忆保留。
- 工作台和只读目录不要求启动 Core。进入原生聊天后如需准备，导航和已有文本保留，输入区显示真实准备或排队状态。失败就地重试，180 秒等待截止后保留恢复入口，不伪装就绪。
- 普通问答直接显示消息。多步骤执行用折叠“执行详情”查看按轮次排列的工具记录；底层参数、输出继续默认折叠。文件成果沿用原预览、下载、版本和续改入口。
- 待补充信息直接在主输入框回答。只有绑定具体提案及指纹的真实操作才出现一次批准/拒绝；模型口头声明的等待确认不能变成通用批准。拒绝或取消后旧确认不会重新生效。
- 普通员工看到可读模型名与可操作错误，诊断码、HTTP 状态和追踪标识保留服务端与原有授权诊断流程。没有自动换模型或放开命令执行。

## 已定位的执行断点

原会话先成功调用查询接口，再保存 `waiting_confirmation`。等待状态阻止后续模型调用时，Host 把本地暂停当作鉴权拒绝，代理进一步将 403 转成 401，原生会话因此持久化 `USER_LLM_PROVIDER_AUTH_FAILED`。仅凭此记录不能判定上游模型凭据失效。

现在可信内部暂停单独返回 409 与暂停标记，由模型代理结束本轮传输；不生成助手内容、不再次调用模型、不把持久任务标为完成。真正 401/403 维持原状态，最小诊断记录不包含密钥或上游正文。

原 `canApprove` 在没有确认对象时返回真，现必须同时存在实际提案和指纹，服务端批准接口也重新校验。原生旧确认还要与当前待处理调用一致；取消记录保留但不作为新授权。

## 同页准备与隔离

服务端注入的首屏占位和 React 加载使用一致的布局骨架，React 挂载后由真实内容替换。桌面启动错误保护仍保留。

`GET /enterprise/conversations/:id/view` 只从当前身份的现有只读 SQLite 获取会话名称及最后 40 条文本（单条最多 16,000 字符），不返回配置、技术提示或工具内部结果。读取前后校验身份；不存在或其他员工会话返回 404。路由必须先于旧会话目录处理器，不唤醒 Core。该暂时快照不替代就绪后的完整分页消息历史。

授权和用户配置仍 no-store；静态哈希资源继续预压缩缓存。Core 最大1、启动并发1、启动等待180秒、空闲120秒和安全检查均未改变。关闭浏览器与主动停止继续分别处理。

## 验收边界

真实公网截图、受控故障、下载文件与服务器只读快照仅保存在本机 `.codex/employee-experience/` 和服务器私有 acceptance 目录。代码、构建通过不代替实际模型/工具/离页验收。具体发布与结论以 PROJECT.md 和该轮私有验收记录为准；未重新巡检全部后台、接口方法或历史办公流程。
