# 员工运行环境与资源效率

基线：`20261025-employee-startup-v1` / `1a17dab1ea647e769c5a4571d7bc9058eb2da796`。
本轮只修改员工 Web、Host 及共享 RC2 客户端；保留 workspace-ui-v6 后台交互，不巡检后台全菜单。

## 已定位的开销

- 登录后主文档先等待 Core；侧栏预取会话、团队、助手、执行器和定时任务。只浏览文件、能力和任务元数据也会启动 Core/Gateway。
- `getCore` 无差别更新 `lastUsed`。可见会话每 30 秒发送 active-lease，纯阅读会话也可能持续保留环境。
- 原容量限制在开始排队前直接拒绝，浏览器通过 readiness 重试获得容量；启动并发队列不能替代运行容量队列。
- 主机 cgroup 实测：Java 控制服务约 509 MiB、监控约 252 MiB、Host 约 68 MiB；数据库约 308 MiB（包含共享及文件页，不能与进程 RSS 重复相加）。单组 Core/Gateway 在三个简单对话期间中位约 45/20 MiB。本轮不因配置上限较大而降低限额。

## 实现边界

- 认证后直接交付品牌应用壳；首页、组织能力、个人记忆、任务历史元数据、文件列表/上传/预览/下载/版本操作通过 Host/RC2，避免创建工作器。
- 组织目录继续直接请求 RC2，有效权限不写个人副本、不长期缓存；所有身份、配置、授权和文件响应保持 no-store。
- Host 只读本人的独立 SQLite WAL 数据库中的界面偏好、系统开关与历史元数据。固定读取当前隔离工作器的 `system_default_user`，不接受客户端身份/SQL/数据库路径；路径检查、只读连接、查询/输出限制与超时；不解密凭据、不迁移、不写库。只合并身份、操作和参数完全相同的在途读取，完成后立即删除。
- 进入新任务、打开会话或高级执行设置仍需 Core：现有模型/助手配置和会话恢复 API 由 Rust Core 实现。仅准备成功后才挂载这些页面并启用执行输入，不把环境等待隐藏到发送消息后。阅读工作台中的历史列表不需要它。
- 文件继续使用 actor profile 的同一持久 workspace；不以启动 Core 获取路径。预览转换原有单转换、大小和超时限制保持。
- WebSocket 被动订阅及后台轮询不创建 Core；空闲关闭继续使用 4001 协议。真实执行响应可以唤醒订阅，页面点击和标签可见性不会唤醒。
- GET/HEAD、文件检查类 POST、工具安装探测、运行态 ensure 和预览释放均不创建休眠 Core，也不延长空闲计时；预览 stop 在已休眠时幂等成功，其余读取明确返回 CORE_NOT_RUNNING，不能伪报成“未安装”。状态读取及前端焦点续租不延长空闲计时；实际修改与任务操作保留占用。Native idle-ready 仍检查运行任务、子进程、团队、工作区状态；未来定时任务仍按既有 due 检查按时唤醒。
- 按 actor 合并启动，运行容量和启动并发统一受限，排队有界，安全释放后自动推进；主动闲置回收不撤销仍有效的员工登录身份。
- 首屏不再导入文件预览、知识和能力编辑等非首页模块。静态 Brotli/Gzip、内容哈希缓存及动态 no-store 保持。
- RC2 相同设备的并发身份复核只合并在途请求；复核结束立刻失效，cookie 变化、下一次请求、撤权仍重新检查。

## 配置与观测

`/srv/apps/zhenwork/shared/config/web.env` 保持 Core=1、启动=1、等待队列=2、启动等待=180000ms、闲置=120000ms；无新增常驻组件，无 Java/数据库/Redis/容器限额调整。

私有证据 `.codex/resource-efficiency/` 包括浏览器网络/性能、真实模型完成、cgroup 每秒采样、定向用例及部署核对。服务以各自 systemd cgroup、Docker 以各自容器 cgroup 统计，区分 anon/file/shared 与实际 current；不把配置上限当实占，不把 cgroup 和其内部进程内存相加。CPU 为区间累计 usage_usec 差，100% 表示单核。

Core本身启动时间没有明显变化：基线5次中位1.373秒（1.293–1.393），最终冷启动/休眠续聊2次中位1.417秒（1.380–1.454）。收益来自不启动不需要的Core，而非加速Rust启动。

最终三次对话：Core累计CPU差冷1.097秒、热0.640/0.659秒；Gateway冷0.168秒、热0.044/0.039秒。一次冷加两次热任务只启动一组环境。每秒采样的任务窗口Core最大current为56.89/60.85/60.73MiB，Gateway26.00/26.84/27.00MiB；包含可回收文件页，不能当作匿名常驻。资源快照中的容器lifetime peak另存，未冒称单任务峰值。基线较早任务窗口Core CPU约0.906/0.512/0.510秒、最大current38.64/42.85/45.66MiB，但测量边界不同，且final容器文件页归属增加，**不能据此宣称单任务CPU或内存下降**。

资源按互不重叠的 systemd/容器 cgroup 统计，1秒采样；文件页与匿名内存分列。PostgreSQL 的 shmem 已包含于 file，不重复累加；重用容器的 lifetime peak 不叫单任务峰值。基线较早三个对话窗口可供 CPU/峰值参考，但其完成时间判定不同，不能与最终任务窗口声称精确 CPU 节省。Java/监控重启后的堆及文件页归属变化也不能算代码节省。

开发定向覆盖冷读取不启动、账号边界、数据库符号链接拒绝、焦点续租、排队合并、闲置关闭保留身份和推进下一员工；v4启动耗时大于闲置阈值的回归用例通过。Host 34项及相关读取/前端/身份定向检查通过，未跑全历史、后台全巡检、Rust/桌面或压测。

## 剩余代价

进入新任务/完整原生会话和高级执行配置仍启动用户独立Core；要继续解除这些页面的Core依赖需迁移原生API，本轮没有整体重写。Core1下另一员工仍需等待当前任务结束和安全闲置回收，实测125.818秒，不等于具备多人同时执行能力。120秒阈值加60秒回收检查带来120–180秒量级闲置窗口，真实运行任务继续保留。未降低服务内存限额、关闭监控或提高常驻资源。

最终发布 `20261025-resource-efficiency-v4`，实际应用 `8a913209a41758cfd13d34e0530911194a218aa6`。管理员网页、Java/监控、23条迁移与linux/amd64精确镜像保持；回滚审核 `shared/config/rollback-reviews/20261025-resource-v4-to-startup-v1.json`，仅退应用/配置，保留数据库、员工文件、历史和授权。

## 回归中发现并修复的第二个误唤醒入口

真实双员工回归中，第二员工正常获得容量并完成模型任务后，第一员工切回文件页产生 `/api/shell/check-tool-installed`。Caddy 记录该只读探测被浏览器取消（499），但原先按 POST 当作活动操作的 Host 启动请求仍排队；173.862 秒后又启动了一次无任务 Core，导致该次 Core0 检查失败。按实际读/执行语义分类后，安装探测、文件检查和运行态 ensure 不能唤醒/续期；预览释放不再为关闭预览启动工作器。每次启动请求记录无凭据的来源分类和 actor 摘要。容量日志改为变化时及十分钟心跳单行记录；授权复核、队列调度和监控频率不变。

失败候选 v1 的首页布局上下文遗漏已按审核回滚并修复；v1/v2 失败证据均保留，不标记通过。最终范围及测量见上文和私有验收记录。

排队/启动耗时不再计入可用 Core 的闲置预算：`lastUsed` 在 ready 时重新起算，再按真实活动续期；既有 120 秒和每 60 秒安全回收检查保持。该问题由 v2 队列时间线与源码确认，增加了启动耗时大于闲置阈值时不得刚就绪就回收的定向用例。
